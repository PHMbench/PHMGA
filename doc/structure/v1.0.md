# PHMGA 重构结构说明（基于现有目录的最小侵入式版本）

## 1. 目标

本次重构不追求把 PHMGA 改造成完全不同的仓库，而是在尽量保留现有目录习惯的前提下，建立一套：

- 配置统一
- graph 可选
- 数据接入清晰
- LLM 后端单一
- DAG 与 TSPN 主链边界明确
- 文档可持续维护

的结构。

核心约束如下：

1. 顶层目录尽量保留：
   - `src/agents`
   - `src/cases`
   - `src/graph`
   - `src/model`
   - `src/tools`
   - `src/schemas`
   - `src/prompts`
   - `src/states`
   - `src/utils`
2. 新增轻量 `src/config/`，仅负责配置解析与合并。
3. 在线 LLM 后端统一使用 OpenRouter。
4. API key 仅保存在 `.env`。
5. 除 secret 外，其余参数统一放入 `config/`。
6. graph 不从 config 中动态拼原子节点，而是**由 config 选择一个已经实现好的 graph builder**。
7. data 部分兼容 PHM-Vibench `data/metadata.xlsx` 的 metadata 驱动方式。
8. 每一层都提供自己的 `structure.md`，并与总文档互相引用。

---

## 2. 当前基础与重构原则

### 2.1 保留现有主目录语义

当前建议保留的主目录含义如下：

- `src/agents`：工作流节点逻辑
- `src/cases`：case runner、实验入口、case 级装配
- `src/graph`：预定义 graph builder 与 graph 相关 helper
- `src/model`：TSPN、桥接、训练、可视化、ML/AutoML 末端实现
- `src/tools`：图外公共工具、算子 schema、数据处理 helper、研究工具
- `src/schemas`：结构化协议对象
- `src/prompts`：LLM prompt 模板
- `src/states`：LangGraph / fallback graph 状态对象
- `src/utils`：日志、路径、通用函数

### 2.2 尽量减少破坏式移动

不建议一次性大范围重命名顶层目录。

建议策略：

- 把重复入口逐步收敛为薄封装
- 把新增能力收进对应目录的子目录
- 通过 `structure.md` 先规范边界，再逐步清理历史遗留文件

## 4.2 Secret 与非 Secret 分离

### `.env` 只允许放：

- `OPENROUTER_API_KEY`
- 其他真正需要保密的 token

### 不允许放入 `.env` 的内容：

## 5. data 设计：兼容 PHM-Vibench metadata

## 5.1 目标

PHMGA 的 data 配置不重新发明一套数据注册系统，而是直接兼容 PHM-Vibench `data/metadata.xlsx` 的 metadata 驱动方式。

也就是说，PHMGA 只负责：

1. 指定 metadata 文件位置
2. 指定缓存 h5 位置
3. 3\. 指定当前实验如何从 metadata 中选择 \`train/val/test\` 样本\
   4\. 指定切片参数（如 \`window\_size\`、\`stride\`、\`slice\_mode\`），并将切片后的样本整理成 PHMState / dataset bundle / train input

---

## 5.2 建议的数据配置拆分

### `config/data/vibench.yaml`

负责数据源全局接入。

```yaml
backend: vibench
metadata:
  path: "/path/to/PHM-Vibench/data/metadata.xlsx"
  format: xlsx
  id_column: Id
  dataset_column: Dataset_id
  label_column: Label
  label_desc_column: Label_Description
  sample_rate_column: Sample_Rate
  length_column: Length
  channels_column: Channels
  reference_column: Reference
cache:
  h5_path: "/path/to/cache.h5"
selection:
  default_mode: fixed_ids
split:
  keys:
    - train_ids
    - val_ids
    - test_ids
window:
  enabled: true
  slice_mode: sliding
  window_size: 4096
  stride: 1024
  drop_last_window: false
  pad_mode: null
```

### `config/data/metadata_schema.yaml`

声明 PHMGA 依赖的最小字段集合。

```yaml
required_columns:
  - Id
  - Dataset_id
  - Name
  - Type
  - File
  - Label
  - Label_Description
  - Sample_Rate
  - Length
  - Channels
optional_columns:
  - Domain_id
  - Working_Condition_description
  - Description
  - Reference
  - Fault_Diagnosis
  - Anomaly_Detection
  - Remaining_Life
  - Digital_Twin_Prediction
```

### `config/experiments/case1.yaml`

只表达本次实验怎么选样本。

```yaml
name: case1
save_dir: /path/to/save
report_path: /path/to/report.md
state_save_path: /path/to/state.pkl
run_executor: true

graph:
  selected: executor_tspn

data_selection:
  mode: fixed_ids
  train_ids: [47050, 47052, 47044, 47046, 47047, 47049]
  val_ids: [47053, 47055]
  test_ids: [47051, 47045, 47048, 47054, 47057]

window:
  slice_mode: sliding
  window_size: 4096
  stride: 1024
  drop_last_window: false

builder:
  min_depth: 4
  max_depth: 8

user_instruction: >
  Analyze the bearing signals for potential faults.
```

## 5.3 允许的数据选择模式

建议支持以下几类 mode：

1. `fixed_ids`
   - 直接使用 `train_ids`、`val_ids` 和 `test_ids`
   - 最贴近现有 case 配置

2. `query_metadata`
   - 用条件从 metadata 中筛选
   - 例如 dataset、condition、label、length、channels

3. `split_from_metadata`
   - 从同一 metadata 条件集自动拆分 `train_ids`、`val_ids`、`test_ids`

4. `predefined_split`
   - 使用配置中预定义的切分方案

此外，数据配置必须显式考虑切片方式，至少包括：
- `window_size`：例如 `4096`
- `stride`：滑窗步长
- `slice_mode`：如 `sliding`、`non_overlapping`
- `drop_last_window`：尾部不足一窗时是否丢弃
- 必要时补充 `pad_mode` 与 `label_alignment`

优先建议：先完整支持 `fixed_ids`，因为它与现有 `case1.yaml`、`case_exp2.yaml`、`tspn_case_exp_ottawa.yaml` 最兼容。

## 6. graph 设计：由 config 选择预定义 graph

## 6.1 核心原则

graph 不从 config 中逐边逐节点地动态拼装。

正确方式是：

- 在 `src/graph/` 中实现好若干明确 graph builder
- 在 config 中只选择“本次运行使用哪一个 graph”

即：

**config 选择 graph，代码实现 graph。**

---

## 6.2 建议保留并扩展的 graph builder

`src/graph/` 建议保留为正式 graph 目录，并逐步吸收当前 `src/graph.py` 与 `src/phm_outer_graph.py` 的职责。

建议结构：

```text
src/graph/
├─ __init__.py
├─ registry.py
├─ builder_loop_graph.py
├─ executor_tspn_graph.py
├─ executor_ml_graph.py
├─ executor_automl_graph.py
├─ research_graph.py
├─ report_only_graph.py
├─ fallback.py
└─ selectors.py
```

说明：

- `builder_loop_graph.py`：plan → execute → reflect 构 DAG
- `executor_tspn_graph.py`：dataset prepare → dag init → tspn bootstrap → deep model train → report
- `executor_ml_graph.py`：shallow ML 末端
- `executor_automl_graph.py`：AutoML 搜索末端
- `research_graph.py`：保留现有 research agent 图
- `report_only_graph.py`：只生成报告
- `registry.py`：graph 名称到 builder 的注册表
- `selectors.py`：根据 config 选择 graph

## 7. `src/config/` 设计

这是本次最重要的新增目录，但它应保持轻量。

建议结构：

```text
src/config/
├─ __init__.py
├─ env_loader.py
├─ config_loader.py
├─ resolver.py
├─ graph_selector.py
├─ experiment_normalizer.py
└─ models.py
```

职责：

- `env_loader.py`：只读 `.env` 中的 secret
- `config_loader.py`：加载 `config/config.yaml` 与 defaults
- `resolver.py`：合并 profile、experiment、graph、layers
- `graph_selector.py`：根据解析后配置选择 graph builder
- `experiment_normalizer.py`：把旧 case 配置归一化为统一 schema
- `models.py`：定义配置对象

不负责：

- 不直接发 LLM 请求
- 不直接构建 graph
- 不直接训练模型

## 8. LLM 后端：统一 OpenRouter，但不偏离现有目录

## 8.1 位置

由于你希望不要偏离太远，建议暂时**不新增顶层 \*\*\*\*src/llm/**，而是把 LLM provider 适配实现放入：

```text
src/utils/llm/
```

或：

```text
src/tools/llm/
```

更推荐：

```text
src/utils/llm/
├─ __init__.py
├─ openrouter_client.py
├─ request_builder.py
├─ response_parser.py
├─ role_registry.py
└─ errors.py
```

这样既满足统一封装，又不破坏当前顶层结构。

---

## 8.2 OpenRouter 规则

### Secret

- `OPENROUTER_API_KEY` 来自 `.env`

### 非 Secret

来自：

- `config/llm/provider/openrouter.yaml`
- `config/llm/roles/default.yaml`
- `config/llm/routing/default.yaml`
- `config/llm/structured_outputs/default.yaml`

### 业务层约束

所有 agent、graph、case 只允许写 role，不允许写实际 model name。

例如：

```yaml
planner_role: planner_llm
reflect_role: review_llm
report_role: report_llm
```

## 10. 推荐的重构依赖方向

只允许：

- `cases -> config`
- `cases -> graph`
- `graph -> agents`
- `graph -> states`
- `agents -> model / tools / prompts / schemas / utils`
- `model -> schemas / utils`
- `tools -> schemas / utils`

禁止：

- `model -> graph`
- `model -> cases`
- `utils -> graph`
- `prompts -> config loader`

一句话：

**上层驱动下层，下层不反向绑死上层。**

## 13. 最小迁移顺序

### Phase 1：配置系统成型

- 新建 `config/config.yaml`
- 新建 `src/config/`
- 将现有 case/model 配置字段映射到新 config system
- 保留旧 yaml 文件名，减少心智切换

### Phase 2：graph 选择器落地

- 在 `src/graph/registry.py` 注册 graph builder
- 用 config 选择 graph
- 根级 `graph.py` / `phm_outer_graph.py` 改为兼容入口

### Phase 3：data metadata 接入标准化

- 抽出 metadata loader
- 抽出 metadata column validator
- 抽出 fixed\_ids 选择器
- 将 current case 的 ref/test 逻辑接入统一 data pipeline

### Phase 4：model 收敛

- 把 DAG→TSPN 桥接明确放入 `src/model/bridge/`
- 把 TSPN runtime/training/visualization 归位
- 把 ML / AutoML 末端并入 `src/model/`

### Phase 5：文档层补齐

- 建立总文档
- 建立 11 个 `structure.md`
- 用引用关系串起来



### 奥卡姆剃刀原则：如非必要，不保留冗余内容；删除或弃用的结构说明统一归档到 `doc/structure/del/`，并在对应文档中注明删减原因与替代去向。

## 14. 最终验收标准

完成后，应满足以下标准：

1. `.env` 中只保留 secret。
2. 所有非 secret 参数均可在 `config/` 中找到。
3. 当前已有 case 配置字段均已映射到新配置系统。
4. 当前已有 model 配置字段均已映射到新配置系统。
5. 数据接入兼容 PHM-Vibench metadata 方式。
6. graph 由 config 选择预定义 builder，而不是运行时动态拼装。
7. 不破坏 `src/agents / cases / graph / model / tools / schemas / prompts / states / utils` 的顶层认知。
8. 每层都有 `structure.md`，并且可以从 README 一路跳转。
9. 每次 run 都能保存 `resolved config` 与 `metadata snapshot`。
10. OpenRouter 成为唯一在线 LLM 后端入口。
