1. 需求与接口对齐（PHMGA ↔ 可解释网络）
   1) 明确数据入口：PHMGA 当前 `InputData.results/ref|tst` 的数组形状、采样率 `fs`、标签来源（root meta.labels）。
   2) 明确网络期望输入：参考 `Unified_X_fault_diagnosis/model/TSPN.py`（`x: [B, L, C]`）与训练所需 label。
   3) 明确输出与解释性目标：分类 logits + 可解释信息（每层算子权重、被选中的算子/特征、关键频带/时域片段等）。
   4) 统一“数据/张量约定”（写入代码校验 + README）：
      - PHMGA 信号：`np.ndarray`，约定形状 `(B, L, C)`。
      - TSPN 输入：`torch.Tensor`，约定形状 `(B, L, C)`；内部如需转置必须转回。
      - 标签：`y: (N,) int64`；`num_classes` 必须在配置中显式给出或由数据推断后“写回并固定”。
   5) 明确“PHMGA DAG 与 TSPN 的关系”（先 A 后 B）：
      - A（推荐，最小侵入）：TSPN 作为“训练后端”，独立于 DAG 的 numpy 算子图；DAG 负责数据选择/切片/基础处理。
      - B（进阶，可选）：把“模型训练/推理/解释”也纳入 DAGTracker（需要新增 node schema 与序列化策略）。
   6) 明确“PHMGA 当前数据组织方式”对 TSPN 的影响（这是集成能否跑通的关键差异）：
      - PHMGA 初始化会**按物理通道拆分**为多个 `InputData` 节点（`ch1..chC`），每个节点的 `results.ref/tst` 是 `{sample_id: (1,L,1)}` 的字典。
      - TSPN 需要**多通道联合输入** `(B,L,C)`；因此训练前必须把同一 `sample_id` 的 `ch1..chC` **按通道顺序拼接**成 `(L,C)`（或 `(1,L,C)`）再喂给模型。
      - 必须约定：通道顺序= `dag_state.channels` 的顺序；样本集合=所有通道 `sample_id` 的交集（缺失则丢弃并记录）。

2. 迁移并“仓库内化”你的可解释网络代码（保持原结构但做最小改造）
   1) 将下列文件按模块化方式迁入 PHMGA（建议路径：`src/model/explainable/`）：
      - `Feature_extract.py` → 特征算子集合（torch 版）
      - `Signal_processing.py` → 信号处理算子集合（torch 版）
      - `TSPN.py` → `Transparent_Signal_Processing_Network`
   2) 清理/隔离外部依赖与路径注入（如 `sys.path.append(current_dir)`），改为包内相对导入。
   3) 建立统一注册表（参考 Unified 中 `ALL_SP / ALL_FE` 的映射）：
      - `ALL_SP`: `'FFT'/'HT'/'WF'/'I'/...` → torch 算子类
      - `ALL_FE`: `'Mean'/'Std'/...` → torch 特征类
   4) 重复算子命名规则（对齐 `config_basic.yaml` 的“可重复列表”）：
      - YAML 允许同一 layer 中重复出现算子名（例如 `['I','WF','I']`）。
      - 构建时自动去重命名：`I, I_1, I_2 ...`（参考 Unified 的 `module_count` 逻辑）。
   5) 解释性“可观测点”固化为统一接口（供 Reporter/保存产物使用）：
      - `get_operator_importance()`：每层 `weight_connection` 的权重/softmax 后的通道分配统计。
      - `get_filter_params()`：`WaveFilters` 的 `f_c/f_b` 分布（mean/std/percentiles）与可复现的响应数据（数组即可）。
      - `get_feature_stats()`：特征层输出的 per-feature 分布/可分性摘要（可选，先留接口）。
   6) 迁移前关键代码 review（必须在 PHMGA 落地时修复/约束，否则训练与解释会不可信）：
      - **复数问题（高优先级）**：`FFTSignalProcessing` 当前返回 complex；但 `InstanceNorm1d/Linear` 默认不支持 complex，且后续 `torch.cat`/loss 也会受影响。
        - 处理策略：FFT 输出改为 `abs()`（幅值谱）或显式拆成 `real/imag` 两通道；并在 `ALL_SP` 中明确该算子的输出 dtype/spec。
      - **权重 in-place 变更（高优先级）**：`SignalProcessingLayer.forward()` 对 `self.weight_connection.weight.data` 做 softmax 并覆盖，这会破坏优化器状态与梯度语义。
        - 处理策略：改为“前向时计算 gating/softmax 权重”但不写回 parameter（例如 `w = softmax(self.weight_connection.weight, dim=0)` 然后用 `F.linear`）。
      - **`squeeze()` 维度风险（中优先级）**：`FeatureExtractorlayer` 使用 `.squeeze()`，当 batch=1 时可能误删 batch 维导致 shape 不稳定。
        - 处理策略：改为显式 reshape（例如 `res = torch.cat(..., dim=1)` 后仅 flatten feature 维，不对 batch 做 squeeze）。
      - **`CustomBatchNorm` 语义混淆（中优先级）**：其 `eps` 既当作“动量”又当作“数值稳定项”，容易导致训练不稳定与解释偏差。
        - 处理策略：优先替换为 `nn.BatchNorm1d`（或明确拆分 `momentum` 与 `eps` 两个参数并修正公式）。
      - **`WaveFilters` 参数维度一致性（中优先级）**：当前用 `args.scale` 初始化 `f_c/f_b` 的“滤波器个数”，但 forward 又按输入通道数切片；容易出现“参数数 < 输入通道数”的隐性截断。
        - 处理策略：把“滤波器数量/每层通道数”的决定权交给 config builder，保证初始化参数与实际通道完全一致（必要时每层独立参数）。
      - **模块顺序与重复命名（低优先级但影响可解释性）**：`ModuleDict` 的 key 顺序将影响“算子索引”的解释映射。
        - 处理策略：保证构建时顺序稳定（使用 `OrderedDict` 或 Python3.7+ 的插入顺序）并在报告里输出 key 列表。

3. 在 PHMGA 引入“可控网络结构”的 YAML 配置协议（参考 `configs/config_basic.yaml`）
   1) 新增并固化一份 PHMGA 侧的模型配置模板（建议：`config/model_tspn_basic.yaml`）：
      - `signal_processing_configs`: layer1..layerN → 操作符列表（允许重复）
      - `feature_extractor_configs`: 特征列表
      - `args`: 与网络结构/训练相关的超参（`in_dim/in_channels/out_channels/scale/skip_connection/...`）
   2) 新增 Pydantic/YAML 校验层：
      - 校验 layer 数、每层 module 数、`out_channels * scale` 能被 module_num 整除等约束
      - 兼容“只给部分 args”的场景（其余由智能体或默认值补全）
   3) 新增 builder：`load_yaml -> build_modules -> build_network`（参考 Unified 的 `model/config.py` 逻辑）。
   4) 建议的 PHMGA 侧 YAML 最小字段（MVP，避免过早复杂化）：
      - `model.name: tspn`
      - `model.signal_processing_configs.layer1..layerN`
      - `model.feature_extractor_configs`
      - `model.args.{device,num_classes,in_dim,in_channels,out_channels,scale,skip_connection}`
      - `train.{learning_rate,batch_size,num_epochs,weight_decay,seed}`
      - `explain.{export_operator_weights,export_filter_params,export_feature_stats}`
   5) 约束校验（必须 fail-fast，避免 silent mismatch）：
      - `in_dim == L`（来自数据摘要）或直接报错并提示：需要 resample/crop（先不做自动 resample）。
      - `in_channels == C`（来自数据摘要）或直接报错并提示：需要通道选择/拼接策略。
      - `num_classes` 与 labels 唯一值数量一致；不一致则终止本轮并写入 `error_log`。

4. 用“智能体”自动化设置/优化模型配置参数（降低先验设计影响）
   1) 新增 `model_config_agent`（规划/提案）：
      - 输入：任务描述、数据摘要（通道数、长度、fs、类别数、样本规模）、当前/历史配置与评估反馈（reflection_history）
      - 输出：可验证的 YAML（或等价 dict），仅修改 `signal_processing_configs / feature_extractor_configs / args`
   2) 新增 `config_reflect_agent`（审视/约束检查 + 是否需要再搜索）：
      - 根据训练指标 + 结构约束失败原因，给出 `needs_revision` 与具体缺口（例如过拟合、算子冗余、通道/维度不匹配）。
   3) 将该“配置搜索环”接入外层图：`Plan(生成/改配置) -> Execute(训练评估) -> Reflect(是否继续)`。
   4) Agent 输出必须“结构化、可重放、可比较”（避免自然语言污染）：
      - `model_config_agent` 输出 JSON（再写入 YAML），字段仅限于 schema 允许的 key。
      - 每轮输出必须包含：`diff_summary`（人类可读）+ `config`（机器可读）。
   5) 搜索策略（先简单再复杂，控制组合爆炸）：
      - Phase-1：固定 layer_num/module_num，仅在候选算子集合中替换与排序（离散搜索）。
      - Phase-2：允许增减层/模块数，但必须满足约束；对每轮变更设置最大 edit distance。
      - Phase-3（可选）：把 `scale/out_channels/skip_connection` 也纳入搜索，但限制范围与步数。
   6) 优化目标的“口径”必须写死（否则智能体无法稳定收敛，也不利于复现）：
      - 主目标（必须）：`val_macro_f1` 或 `val_accuracy`（二选一，建议 macro-F1）。
      - 次目标（建议）：解释性/稀疏性正则（避免网络“看起来可解释但其实每个算子都均匀参与”）：
        - operator 重要性分布的熵（越低越稀疏，但要避免塌陷到单一算子导致性能崩）。
        - 模型复杂度惩罚（层数、总通道数、总参数量、训练耗时）。
      - 约束（必须）：任何违反 schema/shape/整除约束的配置都直接判定为 invalid（不进入训练）。
   7) 配置候选算子集合（必须 whitelist，避免 LLM 输出“不存在算子”）：
      - 初期推荐 whitelist：`I/WF/FFT/HT` + 少量稳定算子；等端到端稳定后再扩展到更多算子族。
      - 每轮变更必须输出“新增/移除/替换”的算子列表与原因（写入 `diff_summary`）。

5. 在执行阶段增加深度模型训练/评估节点（替代或并行于 shallow_ml_agent）
   1) 新增 `deep_model_train_agent`：
      - 从 PHMGA 数据/标签构造 torch DataLoader（支持 ref 训练、tst 评估）
      - 训练日志与指标（acc/f1/confusion matrix/校准等）写回 `PHMState`
   2) 新增可复现实验产物：
      - 保存最终 YAML 配置、权重 checkpoint、指标 JSON/Markdown
      - 与现有 `save_dir` 目录结构对齐
   3) 数据集构造建议（与 PHMGA 现状对齐，先跑通再优化）：
      - MVP 走“原始信号训练”：从根 `InputData` 直接取 `ref/tst` 信号与 `meta.labels`。
      - 说明：`dataset_preparer_agent` 当前做的是“特征文件→X/y”，但 TSPN 需要 `(B,L,C)`，两者不一致；因此不应强行复用。
      - **多通道重建（必须实现）**：对每个 `sample_id`，收集 `ch1..chC` 的 `(1,L,1)`，去掉 batch 维后在最后一维拼接为 `(L,C)`；再在 DataLoader batch 维堆叠为 `(B,L,C)`。
      - **标签编码（必须实现）**：`meta.labels` 的值可能是 int 或 str；训练前需构建稳定的 `label_to_index`（按排序/出现顺序），并把 mapping 保存进 artifacts 以便复现与报告解释。
   4) 训练稳定性与可重复性：
      - 固定 seed；保存 best checkpoint（按 val metric）。
      - 提供 CPU smoke-run（epoch=1, batch=4）用于快速验证与测试。
      - 训练/验证划分建议：从 `ref` 内按 `sample_id` 随机划分 train/val（固定 seed，默认 80/20）；`tst` 只用于最终评估，避免信息泄露。

6. 解释性输出对齐到 PHMGA 的报告系统（Reporter Agent）
   1) 抽取解释性证据：
      - 每层 `weight_connection` 的权重分布（算子重要性/通道分配）
      - 若有 `WaveFilters`，导出 `f_c/f_b` 的统计与可视化
      - 特征层输出的 feature-wise 贡献（可用权重/梯度或消融）
   2) Reporter 生成的 Markdown 报告中：
      - 结论 + 指标
      - “网络结构（来自 YAML）→ 证据链”的逐层解释
      - 附上 DAG（若将模型配置也纳入 DAGTracker）或单独的 workflow 图
   3) 解释性最小可交付（MVP）：
      - Operator importance：每层 top-k 算子（按权重聚合）+ 可视化用数据（CSV/npz）。
      - Filter params：`f_c/f_b` 的分布统计（mean/std/percentiles）+ 典型滤波器响应（数组）。
      - Operator importance 的计算口径（建议在代码与报告中固定，避免“解释漂移”）：
        - `SignalProcessingLayer` 将 `out_channels` 分割成 `module_num` 段，每段对应一个算子模块。
        - 可定义每个算子的重要性为：该算子对应段在 `weight_connection`（以及可选 `skip_connection`）上的权重范数聚合（例如 L1/L2），再做 softmax/归一化得到可比较分数。
        - 报告必须同时输出：算子 key 列表、每层 `module_num`、`out_channels`、以及归一化方式（L1/L2/softmax）。

7. 集成到 PHMGA 的 case 与运行入口
   1) 扩展 `config/case*.yaml`：新增 `model_config_path` 或内联 `model:` 段落用于选择 `TSPN` 工作流。
   2) 新增/修改 `src/phm_outer_graph.py`：
      - 增加一个 executor graph 变体：`prepare -> train_tspn -> report`
      - 或提供开关：`train_backend: shallow_ml | tspn`
   3) 建议的运行方式（面向复现实验）：
      - `case.yaml` 只负责数据与流程开关；`model_config.yaml` 独立维护网络/训练/解释配置。
      - 输出目录：`save/<case_name>/tspn/<timestamp>/`，保存 config、ckpt、metrics、explain artifacts。
   4) 建议增加 “TSPN-only 快速路径”（降低 LLM 成本，便于迭代模型结构）：
      - 当 `train_backend=tspn` 且用户不需要 numpy-DAG 产物时，可跳过 builder loop，直接从 `initialize_state()` 得到的原始信号训练 TSPN。
      - 当 `train_backend=both` 时：先跑 builder（为 shallow_ml 产生特征/数据集），再跑 TSPN（原始信号端到端），最后在 report 中做对比表。

8. 验证与测试（最小可用到可扩展）
   1) 单元测试：YAML 校验、模块构建、前向形状检查（CPU 也可跑）。
   2) 冒烟训练：小数据子集 1~2 epoch，确保端到端可运行与产物落盘。
   3) 依赖补齐：将 `torch`、`einops` 等必要依赖加入 `requirements.txt`（并在 README 标注 GPU/CPU 运行建议）。
   4) 回归边界用例（必须覆盖）：
      - layer 内算子重复（`I, I, I`）能正确构建并前向。
      - `out_channels*scale` 不能整除 module_num 时必须报错（并提示修复方式）。
      - `in_dim/in_channels/num_classes` 与数据不一致时必须报错并写 `error_log`。

## 进一步 review：系统级一致性与可复现实验要求（建议纳入验收）

1) **与 PHMGA 外层图一致性**
   - PHMGA 当前 builder loop 是“LLM 生成 numpy 算子 DAG → 执行 → reflect”；TSPN 是“端到端可训练模型”。
   - 推荐落地路径：将 TSPN 作为 executor graph 的一个分支（`train_backend=tspn|both`），不要强行塞进现有 DAG builder loop（避免两套搜索互相干扰）。
   - **现状差距提醒**：当前 `src/cases/case1.py` 仅运行 builder workflow（executor workflow 被注释），因此“训练后端分支”需要在 case 入口显式启用/补齐，否则配置正确也不会执行到训练。

2) **数据拆分与评价协议（避免“看起来能跑但不可比较”）**
   - `ref_ids/test_ids` 已天然提供 train/test；但 TSPN 训练仍建议从 ref 内部分出 val（固定 seed，比例如 80/20）。
   - 输出指标至少包含：test accuracy、macro-F1、confusion matrix（Markdown/CSV），并保存预测结果（sample_id → pred/true/proba）。

3) **配置与产物的可追溯性（解释性实验的最低要求）**
   - 每次 run 必须保存：
     - `model_config.yaml` 原样拷贝（含 hash 或版本号）
     - 随机种子、git commit（或至少当前工作区 dirty 标记）、依赖版本摘要（pip freeze 可选）
     - checkpoint（best/last）与 metrics.json
   - 解释性产物必须带“层号/算子key/时间戳/数据集信息”，否则后续无法对齐报告与复现。

4) **智能体改配置的安全边界（避免不可控写文件/路径注入）**
   - LLM 只能改 `model_config` 的 whitelist 字段，不能改 `save_dir`、不能改任意路径、不能引入新 import。
   - 每轮改动先过 schema 校验 + 约束校验；失败则回退并写清错误原因到 `reflection_history`。

5) **关键接口函数建议（降低集成耦合度，便于单测）**
   - `build_multichannel_dataset(state, split: 'ref'|'tst') -> (X: np.ndarray, y: np.ndarray, sample_ids: list[str])`
     - 输入来自 `state.dag_state.nodes[ch].results[split]`
     - 输出 `X` 形状 `(N,L,C)`（或 `(N,1,L,C)` 由训练代码决定），并返回 `sample_ids` 方便写预测结果对齐。
   - `validate_model_config_against_data(model_cfg, X, y)`：
     - 校验 `in_dim==L`、`in_channels==C`、`num_classes==len(unique(y))`；失败必须 fail-fast。

6) **数据加载与标签的潜在坑（建议提前修复/写明约束）**
   - `load_signal_data()` 当前对 HDF5 数据做 `np.squeeze()` 后再与 `(sample_length, num_channels)` 比较：
     - 若 `num_channels == 1`，squeeze 很可能把二维 `(L,1)` 压成一维 `(L,)`，导致 shape mismatch 而被跳过。
     - 这会直接影响“单通道数据集”的可用性与 TSPN 的 `in_channels` 推断。
   - 建议策略（择一）：
     - A：修复加载逻辑（仅 squeeze 多余 batch 维，不 squeeze channel 维）。
     - B：在文档/校验中声明：当前仅支持 `num_channels>=2`，并在 case 初始化阶段 fail-fast 给出明确错误。

7) **“可解释”的验收标准建议（避免只输出一堆数字但无法解释）**
   - 必须能回答三类问题，并在报告中有对应小节：
     - 哪些算子/层最重要？（层级、算子 key、分数、归一化口径）
     - `WaveFilters` 学到了什么？（`f_c/f_b` 分布 + 典型响应/频带位置）
     - 特征层输出是否与类别相关？（至少给出类间差异的统计/可视化数据，哪怕是简化版）
   - 必须提供“稳定性检查”（建议至少一种）：
     - 重新训练不同 seed，top-k 算子是否一致（Jaccard/Overlap）。
     - 小幅噪声扰动/随机丢样本时，算子重要性排序是否大幅漂移。

## 进一步 review：解释性语义与实现细节的“隐藏不一致”（建议提前约束/修复）

1) **“算子重要性”是否真的等价于“算子被使用”**
   - 当前 `SignalProcessingLayer` 的结构是：`norm -> Linear(in_channels→out_channels) -> split(out_channels by module_num) -> per-op module -> cat`。
   - 这意味着：
     - Linear 会先把输入通道做混合，再把混合后的通道切片分配给各个算子；
     - 因此“某个算子对应的通道段权重很大”更接近于“该通道段被强调”，并不严格等价“该算子对原始物理通道的重要性”。
   - 建议（先不改结构，先把口径写死）：
     - 报告中明确“重要性=对输出通道段的贡献权重”，而不是“原始通道的物理贡献”；
     - 后续若要更强解释性，再引入更直接的 gating（例如每个算子一个标量 gate/attention）。

2) **FFT/Hilbert/WaveFilters 的“物理频率解释”需要 fs 映射**
   - `WaveFilters` 里 `omega` 目前是 0~0.5 的归一化频率（Nyquist=0.5），并不直接是 Hz。
   - 建议：
     - 在解释性产物里同时输出归一化频率与 Hz（`f_hz = omega * fs`）；
     - 若 `fs` 不可用，报告必须注明“频率为归一化单位”。

3) **torch 侧算子与 PHMGA numpy 算子存在“同名不同义”风险**
   - 例如 `mean/std/var/entropy`：PHMGA 里是 numpy 聚合算子（AggregateOp），Unified 里是 torch feature 提取模块。
   - 建议：
     - 在 `src/model/explainable/` 内部统一用前缀/命名空间（例如 `TorchMeanFeature` 或在注册表里加域名 `fe:Mean`、`sp:FFT`）；
     - 报告生成时打印完整路径/类别（SP vs FE）避免歧义。

4) **依赖管理：`torch` 不建议直接 pin 进 `requirements.txt`**
   - 原因：torch 轮子与 CUDA/平台强绑定，pip 直接依赖容易在不同机器上失败或拉错版本。
   - 建议：
     - README/文档里提示用户按平台安装 torch（CPU/CUDA），PHMGA 只做 import 级别的可选依赖检查；
     - 或新建 `requirements-torch.txt` / `extra_requires`（若未来做 packaging）。

5) **标签与数据泄露边界（建议文档写清 + 代码保护）**
   - 当前初始化把 `ref_labels` 与 `test_labels` 合并到 `meta.labels`（用于评估很方便）。
   - 但在“真实部署”或某些 benchmark 设置里，test label 应视为未知；训练/配置搜索不应读取 test label。
   - 建议：
     - state/meta 同时存 `labels_ref` 与 `labels_tst`，并在训练代码中强制只用 `labels_ref`；
     - 评估阶段才允许读取 `labels_tst`（若存在），否则只输出预测不算指标。
